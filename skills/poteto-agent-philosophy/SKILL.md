## 哲学概览

土豆姐的 Agent 编排哲学可以用一句话概括：

> **"给 Agent 一个目标和一种验证方式。"**
> — Lauren Tan

传统方式是：开发者下达指令 → AI 写代码 → 编译通过 → 声称"完成"。
这会产生大量未经验证的"AI 垃圾代码"（slop code）。

Poteto 的方法论颠覆了这个流程：

```
开发者意图 → 路由到 Playbook → 结构化任务分解 → 子代理并行执行
    → 每步必须提供运行时证据 → 对抗性多模型审查 → 确认完成
```

### 三个不可动摇的信条

1. **永远不要相信"Done"** — Agent 说完成了不代表真的完成了，必须有运行时证据
2. **结构化优于即兴** — 用 Playbook 约束 Agent 行为，而非让其自由发挥
3. **工具即产出** — 写脚本、写自动化工具、写验证器，而非手动操作

## 十大设计原则

这是 pstack 框架中核心的 10 条设计原则，指导 Agent 在每一步做出正确决策：

### 1. 🦥 懒惰协议 (Laziness Protocol)

> 写代码对 AI 来说太容易了，这反而导致过度工程化。

- **偏向删除**：优先寻找删除死代码、简化调用层级的机会
- **最小化 diff**：执行能完全解决问题的最小变更
- **合并决策点**：不要在多个文件中散布重复逻辑

```
❌ 错误: 为一个简单功能创建 5 个新文件和 3 层抽象
✅ 正确: 在现有文件中用 20 行代码解决问题
```

### 2. 🏗️ 基础思维 (Foundational Thinking)

在写逻辑之前，先确立：
- 核心类型和数据结构
- 脚手架 vs 功能的开发顺序
- 并发参与者之间共享什么

### 3. 🔄 从第一性原理重新设计 (Redesign from First Principles)

当集成新需求到已有设计中时，假装这个需求从第一天就存在来重新设计，而非在现有代码上打补丁。

### 4. ⚔️ 攻击前提 (Attack the Premise)

如果基于同一前提的两个或更多修复都失败了，把前提写下来并直接测试它，然后再写新的修复。

### 5. ➖ 先减后加 (Subtract Before You Add)

在做添加、重构或重写时：先清除死代码，再在更简洁的基础上构建。

### 6. 📖 最小化阅读负担 (Minimize Reader Load)

- 计算层级和隐藏状态
- 折叠单调用者的包装函数
- 缩小可变作用域

### 7. 🎯 结果导向执行 (Outcome-Oriented Execution)

对于有明确阶段边界的重写和迁移，直接收敛到目标架构，而非保留一次性兼容状态。

### 8. 👤 体验优先 (Experience First)

在产品、UX、功能范围的权衡中，选择用户愉悦感而非实现便利性。

### 9. 🔬 穷尽设计空间 (Exhaust the Design Space)

面对新的交互或架构决策时，构建 2-3 个竞争原型并排比较，然后再做承诺。

### 10. 🔧 构建杠杆 (Build the Lever)

> 工具本身就是可以让审查者重新运行的产出物。

适用于所有非平凡工作。构建能完成或证明工作的工具（如 codemod、脚本、生成器或子代理技能），而非手动操作。

```
❌ 错误: 手动逐个文件修改 50 处 API 调用
✅ 正确: 写一个 codemod 脚本来批量转换，脚本本身就是可审查的产出
```

## 24 条 Agent 编码准则

### Part 1: 与人类协作 (Pair with the Human)

| # | 准则 | 说明 |
|---|------|------|
| 1 | **可理解的产出** | 代码必须干净到可以异步审查和维护 |
| 2 | **前置上下文声明** | 非平凡任务开始前，陈述问题、关键假设和成功标准 |
| 3 | **解释重大决策** | 推理过程要关联具体代码和观察到的运行时行为，而非猜测 |
| 4 | **保持提交可分离** | 写有意义的提交历史，解释为什么行为发生了变化 |
| 5 | **优化正确性** | 优先关注经过审查的、可工作的成果，而非代码量或 PR 数量 |

### Part 2: 用证据赢得信任 (Earn Trust with Evidence)

| # | 准则 | 说明 |
|---|------|------|
| 6 | **证据先于信心** | 在形成诊断前先检查相关代码；未验证的解释必须标记为"假说" |
| 7 | **先复现再修复** | Bug 修复前必须先复现问题，修复后用相同步骤确认已解决 |
| 8 | **操作真实接口** | 驱动用户实际交互的界面（UI/CLI/API），而非仅依赖单元测试 |
| 9 | **可复用的验证产物** | 构建可重复运行的验证脚本或测试钩子，让验证每次都能相同地执行 |
| 10 | **隔离变更** | 永远不要同时堆叠多个未测试的变更；严格执行"一次变更，一次验证" |

### Part 3: 把代码库当作记忆 (Treat the Codebase as Memory)

| # | 准则 | 说明 |
|---|------|------|
| 11 | **先检查周边约定** | 生成新代码前先检查本地模式和文档 |
| 12 | **复制前验证** | 不要盲目复制代码库中已有的模式——Agent 同样容易复制坏模式 |
| 13 | **修复根因** | 解决范围内的底层结构问题，而非叠加临时方案 |
| 14 | **清理脚手架** | 完成前删除排查过程中引入的临时诊断代码、日志或脚手架 |
| 15 | **避免永久注释堆积** | 不要把临时的代码审查评论变成永久的注释或通用规则 |

### Part 4: 改善环境 (Improve the Environment)

| # | 准则 | 说明 |
|---|------|------|
| 16 | **可执行约束优于注释** | 优先使用架构设计、严格类型、lint 规则和 CI 检查 |
| 17 | **测试新规则** | 验证新的 lint 检查能正确拒绝坏代码同时允许有效代码路径 |
| 18 | **泛化原则** | 干净地记录通用约束，不要把项目特定的名称烘焙到全局指南中 |
| 19 | **尊重范围边界** | 不要让项目特定的限制错误地渗透到通用规则中 |
| 20 | **限定重构范围** | 超出当前任务范围的架构重构应作为独立的后续任务 |

### Part 5: 逐步扩展信任 (Scale Trust Gradually)

| # | 准则 | 说明 |
|---|------|------|
| 21 | **全新会话评估** | 使用干净、隔离的会话来评估 Agent 指令和 prompt 性能 |
| 22 | **隔离预期答案** | 将预期目标答案与被评估的 Agent prompt 流程隔离 |
| 23 | **增量精炼** | 隔离故障并调整最小的相关指令，而非重写整个规则块 |
| 24 | **渐进自治** | 只有在运行时验证闭环完全功能化且可复现后，才扩展委托并允许 Agent 独立合并或推送 |

## Playbook 驱动开发

### 什么是 Playbook？

Playbook 是预先编写的、映射到特定工程任务的结构化步骤程序。pstack 包含 23+ 个不同类型的 Playbook：

| Playbook 类型 | 适用场景 | 核心流程 |
|--------------|---------|---------|
| **Bug Fix** | 修复缺陷 | 复现 → 定位根因 → 最小修复 → 验证 → 回归测试 |
| **Feature** | 新功能开发 | 需求分析 → 架构设计 → 原型 → 实现 → 集成测试 |
| **Refactor** | 代码重构 | 识别问题 → 设计目标架构 → 增量迁移 → 验证行为不变 |
| **Investigation** | 调查问题 | 收集证据 → 形成假说 → 验证/反证 → 报告结论 |
| **Performance** | 性能优化 | 基线测量 → 瓶颈定位 → 优化 → 对比测量 → 验证 |
| **Review** | 代码审查 | 读取 diff → 理解意图 → 检查正确性 → 检查风格 → 反馈 |
| **Ship** | 发布上线 | 检查清单 → 集成测试 → 构建 → 部署 → 冒烟测试 |
| **Orchestrate** | 宏观编排 | 分解大目标 → 分配子任务 → 并行执行 → 收集结果 → 整合 |

### Playbook 路由机制

```
用户输入: "/poteto-mode 修复导出功能的重复行 bug"

poteto-mode 路由器:
  1. 分析意图 → 识别为 "Bug Fix" 类型
  2. 加载 Bug Fix Playbook
  3. 输出结构化任务清单:
     □ 复现: 执行导出功能，确认看到重复行
     □ 定位: 追踪数据流，找到重复发生的位置
     □ 修复: 应用最小变更修复根因
     □ 验证: 重新执行导出，确认无重复行
     □ 回归: 确认其他导出格式仍正常工作
  4. 逐步执行，每步要求证据
```

## 子代理编排 (Subagent Orchestration)

### 无畏并行 (Fearless Parallelism)

传统的 Agent 并行会导致混乱——多个 Agent 同时修改同一代码库，产生冲突。
Poteto 的方案通过三个机制实现"无畏并行"：

#### 1. 包装模式 (Wrapper Pattern)

每个子代理在执行前都必须重新加载核心操作手册：

```
// poteto-agent 包装
每个子代理启动时:
  1. 加载 poteto-mode 核心原则
  2. 加载当前任务的 Playbook
  3. 在隔离环境中执行（独立的 git worktree / 分支）
  4. 返回结果 + 验证证据
```

#### 2. 隔离执行

每个子代理工作在独立的环境中：
- 独立的 git worktree 或分支
- 独立的上下文窗口
- 严格界定的任务范围

#### 3. 门控交付 (Gated Deliverables)

子代理不能仅返回代码——必须返回代码 + 验证证据的捆绑包。

### 编排拓扑

```
                    ┌─────────────┐
                    │ Orchestrator│
                    │  (主编排器)   │
                    └──────┬──────┘
              ┌────────────┼────────────┐
        ┌─────▼─────┐ ┌───▼────┐ ┌─────▼─────┐
        │Sub-coord-1│ │Worker-A│ │Sub-coord-2│
        │(子协调器)  │ │(工人)   │ │(子协调器)   │
        └─────┬─────┘ └────────┘ └─────┬─────┘
         ┌────┼────┐              ┌────┼────┐
      ┌──▼─┐ ┌▼──┐ ┌▼──┐     ┌──▼─┐ ┌▼──┐ ┌▼──┐
      │W-1 │ │W-2│ │W-3│     │W-4 │ │W-5│ │W-6│
      └────┘ └───┘ └───┘     └────┘ └───┘ └───┘
```

**关键约束**: 编排深度有限（通常 orchestrator → sub-coordinator → worker 三层），防止 token 消耗失控和状态丢失。

## 对抗性审查 (/interrogate)

### 为什么需要多模型对抗？

不同的前沿模型有不同的优势和盲点。依赖单一模型自我审查就像让一个人自己检查自己的考试。

### 工作机制

```
代码 diff + 上下文
       │
       ├──→ [Model A: Claude] ──→ 审查意见 A
       │
       ├──→ [Model B: GPT-4] ──→ 审查意见 B
       │
       └──→ [Model C: Gemini] ──→ 审查意见 C
                  │
          ┌───────▼───────┐
          │  共识分析器     │
          │ 重叠批评 = 高置信│
          │ 独立批评 = 需评估│
          └───────────────┘
```

### 对抗性审查规则

1. **多样性**: 使用不同家族/不同配置的模型
2. **交叉验证**: 多个模型同时指出的问题具有最高置信度
3. **边界测试**: 每个模型检查边缘情况和逻辑缺陷
4. **自动化**: 人类审查者只需权衡共识，而非手动寻找基本 bug

## 验证闭环 (Verification Loop)

这是 poteto 哲学中最核心的机制——没有验证，一切都是空谈。

### 验证层级

```
Level 0: 编译通过          ← 几乎无意义（只证明语法正确）
Level 1: 类型检查通过       ← 基础保障
Level 2: 单元测试通过       ← 局部正确性
Level 3: 集成测试通过       ← 组件协作正确
Level 4: 真实接口运行验证   ← ✅ Poteto 的最低标准
Level 5: 用户行为路径验证   ← ✅ 理想目标
```

### "Prove It Works" 执行模板

```markdown
## 验证检查清单

### 修改前
- [ ] 复现了原始问题（截图/日志/输出）
- [ ] 记录了复现步骤

### 修改后
- [ ] 用相同步骤验证问题已修复
- [ ] 提供了运行时证据（截图/日志/输出）
- [ ] 确认无回归（相关功能仍正常工作）
- [ ] 验证脚本/命令已提交到仓库

### 证据附件
- 修改前输出: [附件]
- 修改后输出: [附件]
- 验证命令: `[可重复执行的命令]`
```

## 实战工作流模板

### 模板 A: 标准 Bug 修复

```markdown
# Bug Fix Workflow

## Step 1: 理解问题
- 阅读 bug 报告
- 识别受影响的代码路径
- 确定预期行为 vs 实际行为

## Step 2: 复现
- 设置环境
- 执行触发 bug 的具体步骤
- 捕获证据（日志、截图、输出）
- 如无法复现 → 停止，向人类报告

## Step 3: 定位根因
- 从症状追溯到源头
- 检查数据流、状态变化、竞态条件
- 标记确认的根因位置

## Step 4: 最小修复
- 应用 [懒惰协议]：最小变更
- 不引入新的抽象层
- 不"顺便"重构无关代码

## Step 5: 验证
- 用 Step 2 相同的步骤验证
- 确认 bug 不再出现
- 运行回归测试
- 提供运行时证据

## Step 6: 交付
- 清理临时调试代码
- 写清晰的提交信息
- 附上验证证据
```

### 模板 B: 功能开发

```markdown
# Feature Development Workflow

## Step 1: 需求对齐
- 明确功能目标和用户故事
- 确认成功标准
- 识别边界条件

## Step 2: 设计
- 分析现有代码库的模式和约定
- 应用 [穷尽设计空间]：草拟 2-3 个方案
- 选择最简洁、最符合现有架构的方案

## Step 3: 基础搭建
- 应用 [基础思维]：先定义数据结构和类型
- 搭建核心接口
- 不写实现细节

## Step 4: 增量实现
- 逐步添加功能，每步验证
- 应用 [隔离变更]：一次一个功能点
- 持续运行测试

## Step 5: 集成验证
- 在真实环境中运行
- 驱动用户实际交互路径
- 记录运行时证据

## Step 6: 审查与精炼
- 应用 [最小化阅读负担]
- 移除不必要的复杂性
- 确保代码自文档化
```

### 模板 C: 编排大型任务

```markdown
# Orchestration Workflow

## Step 1: 分解
- 将大目标拆分为独立的子任务
- 识别依赖关系和并行机会
- 为每个子任务分配 Playbook 类型

## Step 2: 并行分发
- 为每个独立子任务启动子代理
- 每个子代理加载 poteto-mode + 对应 Playbook
- 子代理在隔离环境中执行

## Step 3: 收集与整合
- 收集每个子代理的结果 + 验证证据
- 解决冲突和重叠
- 按依赖顺序整合变更

## Step 4: 全局验证
- 在整合后的代码上运行完整测试套件
- 执行端到端验证
- 对抗性审查最终 diff

## Step 5: 交付
- 生成综合报告
- 附上所有子任务的验证证据
- 清晰标注每个变更的原因
```

## 游戏开发编排案例

土豆姐展示了如何用 Agent 编排工作流高效制作游戏。以下是从她的推文中提炼的方法论：

### 游戏开发的 Agent 角色分配

```
┌────────────┐    ┌────────────┐    ┌────────────┐
│  Producer   │    │  Architect  │    │  QA Tester  │
│  (制片人)    │    │  (架构师)    │    │  (测试员)    │
│             │    │             │    │             │
│ - 任务拆分   │    │ - 系统设计   │    │ - 编写测试   │
│ - 优先级排序 │    │ - 技术选型   │    │ - 运行验证   │
│ - 进度跟踪   │    │ - 接口定义   │    │ - 捕获证据   │
└──────┬──────┘    └──────┬──────┘    └──────┬──────┘
       │                  │                  │
       └──────────────────┼──────────────────┘
                   ┌──────▼──────┐
                   │   Coder(s)   │
                   │   (编码者)    │
                   │              │
                   │ - 实现功能    │
                   │ - 遵循 Playbook│
                   │ - 提交+证据   │
                   └──────────────┘
```

### 游戏开发工作流

```markdown
# Game Dev Orchestration

## Phase 1: 核心机制
- 定义游戏核心循环 (Core Loop)
- 实现基础物理/交互系统
- 验证: 手动测试核心机制是否"感觉对"

## Phase 2: 内容管线
- 并行启动多个 Worker:
  - Worker A: UI/HUD 系统
  - Worker B: 关卡/场景系统
  - Worker C: 音效/视觉效果
- 每个 Worker 独立验证

## Phase 3: 集成
- 合并所有 Worker 的产出
- 全局游戏流测试
- 自动化回放测试验证

## Phase 4: 抛光
- 对抗性审查：让不同模型试玩并报告体验
- 性能优化
- 边缘情况处理
```

### 关键洞察

1. **确定性测试**: 像测试 Web 应用一样测试游戏——写自动化测试脚本验证游戏机制
2. **管理引擎上下文**: 用精确的引擎文档（Godot/Unity/Unreal）喂给 Agent，避免幻觉已废弃的 API
3. **不是"Vibe Coding"**: 不是让 AI 凭感觉生成整个游戏，而是人类管理架构约束，Agent 处理实现和回归测试

## Agent 行为指令模板

以下模板可以直接用于配置你的 AI Agent 行为。复制到你的项目规则文件中即可：

```markdown
# Agent 操作规范

## 核心身份
你是一个纪律严明的工程搭档，不是一个代码生成器。
你的目标不是产出最多的代码，而是产出最正确的代码。

## 执行协议

### 开始任务前
1. 陈述你对问题的理解
2. 列出关键假设
3. 定义成功标准
4. 选择适用的 Playbook

### 执行任务中
1. 遵循选定 Playbook 的步骤
2. 每个步骤完成后提供证据
3. 遇到歧义时停下来问，不要猜
4. 应用懒惰协议：最小变更

### 完成任务时
1. 运行验证：驱动真实接口
2. 提供运行时证据（日志/截图/输出）
3. 确认无回归
4. 清理临时代码

## 禁止行为
- ❌ 声称"完成"但不提供运行时证据
- ❌ 同时堆叠多个未验证的变更
- ❌ 盲目复制代码库中已有的模式
- ❌ 引入不必要的抽象层
- ❌ "顺便"重构超出任务范围的代码
- ❌ 将临时注释变成永久代码
- ❌ 生成大量代码后说"剩下的类似，你来完成"

## 鼓励行为
- ✅ 先复现问题再修复
- ✅ 写可重复运行的验证脚本
- ✅ 用工具解决批量问题（Build the Lever）
- ✅ 探索 2-3 个设计方案再决定
- ✅ 主动删除死代码和简化结构
- ✅ 在提交信息中解释"为什么"
```

## 快速参考卡

| 场景 | 适用原则 | 行动 |
|------|---------|------|
| 修 Bug | 验证闭环 | 先复现，后修复，再用同步骤验证 |
| 新功能 | 穷尽设计空间 | 草拟 2-3 方案，选最简洁的 |
| 重构 | 懒惰协议 | 先减后加，最小化 diff |
| 大任务 | 无畏并行 | 分解 → 隔离子代理 → 门控交付 |
| 审查 | 对抗性审查 | 多模型交叉验证，共识 = 高置信 |
| 性能 | 结果导向 | 基线测量 → 优化 → 对比测量 |
| 发布 | Prove It Works | 端到端冒烟测试 + 运行时证据 |
| 游戏 | 多角色编排 | Producer/Architect/Coder/QA 分工 |
